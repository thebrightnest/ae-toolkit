# Parallel Execution in aet-work

## Bash Job Control Approach

The orchestrator script generated by `aet run` uses bash job control to manage concurrent tasks. No external tools (like `parallel`, `xargs -P`, or Python threads) are required.

### Main Loop Structure

```bash
# Detect concurrency cap
JOBS="${AET_WORK_JOBS:-4}"
[[ "$JOBS" -gt 8 ]] && JOBS=8

active=0
failed=0

while tasks_remain; do
  if [[ $active -lt $JOBS ]] && unblocked_tasks_exist; then
    task=$(next_unblocked_task)
    spawn_task "$task" &
    ((active++))
  fi

  if [[ $active -gt 0 ]]; then
    wait -n  # bash 4.3+: wait for any background job
    exit_code=$?
    ((active--))

    if [[ $exit_code -ne 0 ]]; then
      mark_failed "$task"
      failed=1
    else
      mark_done "$task"
      promote_dependents "$task"
    fi
  fi

  if [[ $failed -eq 1 ]] && [[ $active -eq 0 ]]; then
    exit 1
  fi

done

# Drain remaining jobs
while [[ $active -gt 0 ]]; do
  wait -n
  ((active--))
done

[[ $failed -eq 1 ]] && exit 1 || exit 0
```

### Why `wait -n`

Bash 4.3 introduced `wait -n`, which blocks until any background job completes. This is the primitive that enables the slot-pool pattern:

- When a slot frees up, `wait -n` returns immediately
- The orchestrator promotes dependents and fills the slot with the next unblocked task
- If no tasks are unblocked, the loop simply waits for the next `wait -n` return

On macOS, the default bash is often older than 4.3. The orchestrator template falls back to a polling loop (`sleep 1` + `jobs -p` check) when `wait -n` is unavailable.

## Concurrency Cap Algorithm

The cap is determined in this order:

1. **`AET_WORK_JOBS` environment variable** — user override, highest priority
2. **OS detection** — `nproc` on Linux, `sysctl -n hw.ncpu` on macOS
3. **Hard fallback** — `4` if neither detection method works
4. **Upper bound** — min(detected value, 8)

The upper bound of 8 prevents accidental fork bombs on machines with many cores (e.g., 64-core servers). Eight concurrent agent CLI processes each consuming 2–4 GB of context is already a heavy load.

## Resume Behavior Under Parallelism

Resume semantics are preserved from sequential mode with one addition for orphaned in-progress tasks.

### Normal Resume

- `done` tasks are skipped entirely
- `blocked` tasks that have become unblocked since the last run are picked up immediately
- `failed` tasks are re-attempted (the user must have fixed the issue)

### Orphaned In-Progress Tasks

If a previous orchestrator run crashed or was killed, some tasks may still be marked `in-progress` in the queue but have no running process. On startup, the orchestrator:

1. Checks each `in-progress` task for a detectable running PID
2. If no PID is found, prints a warning and marks the task `failed`
3. The user inspects the worktree, decides whether work was lost, and either fixes or resets the task

This avoids the ambiguity of "is this task still running somewhere?" without requiring a persistent process registry.

## State Machine Under Parallelism

| Status transition           | Trigger                                          |
| --------------------------- | ------------------------------------------------ |
| `unblocked` → `in-progress` | Task picked up by orchestrator, worktree created |
| `in-progress` → `done`      | Agent CLI exits 0                                |
| `in-progress` → `failed`    | Agent CLI exits non-zero                         |
| `blocked` → `unblocked`     | All `blocked_by` entries are `done`              |

Race condition avoidance: since only the main loop mutates the queue file and bash job control guarantees only one `wait` returns at a time, no file-locking mechanism is required.
